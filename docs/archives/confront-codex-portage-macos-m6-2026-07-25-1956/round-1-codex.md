# Round 1 - Analyse Codex du plan M6

## 1. Ce que j'approuve

J'approuve l'axe principal : **une seule run loop AppKit sur le fil principal, possedee par rumps quand le tray existe**. Le code actuel a deja la bonne couture : `serve_macos()` injecte `run_loop` (`src/aparte/macos_runloop.py:37-45`), demarre le serveur HTTP sur un fil daemon (`src/aparte/macos_runloop.py:58`), puis inscrit le raccourci dans `on_ready()` (`src/aparte/macos_runloop.py:62-84`). Le plan ne tente pas de lancer `rumps.App.run()` et `AppHelper.runEventLoop()` cote a cote, ce qui est la bonne contrainte.

J'approuve aussi la propriete du `RecordingController`. Le code est clair : `run_desktop()` recupere `(handler, controller)` (`src/aparte/desktop.py:93-95`), le passe a `serve_macos()` sur Darwin (`src/aparte/desktop.py:100-108`), et le handler n'expose qu'une route GET de lecture (`src/aparte/desktop.py:298-307`). Les commentaires verrouillent explicitement que `run_desktop()` possede le controleur et que le handler observe (`src/aparte/desktop.py:535-550`). Le tray doit rester dans ce modele : observer l'objet deja possede, ne pas recreer un controleur, ne pas passer par une route POST.

Le sondage du controleur par le tray est un bon compromis pour M6. Pour `state`, une lecture de reference de chaine est suffisante pour afficher un etat grossier, et elle evite d'introduire une dependance du controleur vers AppKit. Le precedent Linux existe : le tray GTK sonde l'etat de session via `GLib.timeout_add_seconds()` (`src/aparte/tray.py:138-156`). Le passage a 0,25 s sur Mac est defendable parce que le probleme M8 etait un doute immediat apres appui, pas une supervision longue.

Le deplacement du demontage dans une fonction idempotente passee au tray est necessaire. Le `finally` actuel ne protege que les chemins ou `run_loop()` rend la main (`src/aparte/macos_runloop.py:85-98`). Or le chemin rumps standard passe par `quit_application()`, qui appelle `NSApplication.terminate_`; la documentation PyObjC indique aussi que `AppHelper.runEventLoop()` ne retourne pas sauf exception. Appeler le demontage avant de demander la terminaison est donc la bonne idee de base.

Le decoupage "vue pure puis liaison rumps mince" est solide. Avec les contraintes du projet, les tests doivent tourner sous Linux sans PyObjC, Carbon, PortAudio ni rumps. Un `tray_view(...)` pur, des labels fr/en, un `format_elapsed()`, puis un `MacTray` mince et injectable, c'est le bon niveau de testabilite.

J'approuve le choix d'icones template monochromes. `PRODUCT.md` impose que l'etat d'enregistrement ne repose pas sur la couleur seule (`PRODUCT.md:147-150`), et `DESIGN.md` impose le contraste calcule pour les couleurs visibles (`DESIGN.md:519-526`). Dans une barre de menus translucide, laisser macOS teinter l'image est plus robuste qu'un carmin fixe.

J'approuve de remonter la preservation de l'extra `[macos]` dans `_installed_extras()`. Aujourd'hui la fonction ne preserve que `whisper`, `recording` et `cuda` (`src/aparte/update.py:152-165`), alors que `pyproject.toml` declare deja `rumps` et les frameworks PyObjC dans l'extra macOS (`pyproject.toml:52-58`). Si M6 livre un item de mise a jour, il ne doit pas pouvoir reinstaller une app macOS sans ses dependances macOS.

## 2. Ce que je desapprouve

Je desapprouve la modification globale de contrat `run_loop(on_ready)` -> `run_loop(on_ready, on_quit)` telle qu'elle est formulee. `run_hotkey_diagnostic()` utilise le meme seam et appelle encore `run_loop(on_ready)` (`src/aparte/macos_runloop.py:117-169`). Si `_appkit_run_loop` devient strictement binaire, le diagnostic M8 casse sur son chemin par defaut. Le deuxieme argument doit etre optionnel (`on_quit=None`), ou bien `serve_macos()` doit adapter son propre runner sans changer le contrat du diagnostic.

Je desapprouve l'affirmation "le timer rumps est le seul point d'accroche apres lancement" comme certitude technique. Le code actuel a ete valide en M8 avec une inscription Carbon faite apres `NSApplication.sharedApplication()` mais avant `AppHelper.runEventLoop()` (`src/aparte/macos_runloop.py:172-192`, `docs/plan-portage-macos-m8.md:41-45`). Le source rumps actuel confirme que `App.run()` effectue son setup puis appelle `AppHelper.runEventLoop()`, et que `Timer` est repetitif par construction. Le timer est probablement acceptable, mais le plan doit specifier le one-shot reel : timer retenu fortement, `start()`, `stop()` en `finally`, et callback protege contre double execution.

Je desapprouve le pseudo-code qui remet `SIGINT` a `SIG_DFL` avant `self._app.run()` comme si cela preservait l'invariant M5. Le source rumps appelle `AppHelper.installMachInterrupt()` dans `App.run()` juste avant la run loop, et le changelog rumps 0.4.0 dit que les interruptions clavier arretent maintenant une application en cours. Donc rumps peut reinstaller un comportement SIGINT apres notre `signal.signal(...)`. Ce n'est pas forcement grave, mais le plan ne peut pas continuer a raisonner comme si le chemin rumps avait le meme Ctrl-C brutal que `_appkit_run_loop`.

Je desapprouve le chemin "Mettre a jour" en l'etat s'il est presente comme fiable. Le plan propose `apply_update()` puis `restart()` depuis un worker, mais le plan global macOS disait explicitement que `os.execv(sys.executable, argv)` relance l'interpreteur/module, pas forcement l'application responsable vue par TCC, et qu'il faudra redemarrer via bundle ou LaunchAgent (`docs/plan-portage-macos.md:307-315`). Tant que M7 n'a pas livre cette identite de relance, M6 ne devrait pas promettre une mise a jour Mac propre. Au minimum, l'item doit etre scope "experimental checkout/interpreteur courant", ou l'installation doit etre differee a M7.

Je desapprouve aussi l'implicite "CLI update" herite du plan global. Dans le code actuel, le parser CLI n'expose pas de commande `update` (`src/aparte/cli.py:140-215`). Si le plan M6 mentionne "tray ou CLI", il faut soit ajouter cette commande, soit cesser de la citer comme chemin existant.

Je desapprouve l'idempotence basee seulement sur `threading.Event` si `teardown()` peut etre appele depuis plus d'un chemin. `is_set()` puis `set()` n'est pas un compare-and-set protege, et marquer "torn" avant les operations fait qu'une exception prematuree empeche toute tentative ulterieure. Dans ce code, la plupart des appels seront probablement sur le fil principal, mais le contrat annonce est "idempotent" : il doit etre protege par un verrou et chaque etape critique doit etre best-effort pour que `server_close()` ne depende pas de la reussite de l'etape precedente.

## 3. Ce qui manque

Il manque un point rumps concret : **desactiver le Quit par defaut**. `rumps.App` ajoute automatiquement un item Quit dont le callback est `rumps.quit_application()` si `quit_button` n'est pas `None`. Si M6 ajoute son propre "Quitter" mais oublie `quit_button=None`, il y aura soit deux items Quit, soit un chemin visible qui contourne totalement `teardown()`.

Il manque un hook de terminaison autre que l'article "Quitter". Un utilisateur peut quitter via un chemin systeme, une terminaison de session, ou un comportement rumps interne. Le source rumps expose `events.before_quit` via `applicationWillTerminate_`; il faut y raccrocher `teardown()` aussi, de facon idempotente. L'article "Quitter" doit appeler `teardown()` avant `quit_application()`, mais il ne doit pas etre le seul filet.

Il manque la course entre le `Timer` d'`on_ready` et une sortie tres rapide. Avec l'approche timer, `on_ready()` devient asynchrone par rapport a la construction du menu. Il faut que `on_ready()` fasse `if torn: return` avant d'inscrire le raccourci, et que le timer one-shot soit arrete quoi qu'il arrive. Sinon un Quit tres rapide peut demonter le serveur puis enregistrer un hotkey apres coup.

Il manque le cas "Quitter pendant demarrage de capture". `RecordingController._start_locked()` appelle `ensure_microphone_access()` sous `_lock` (`src/aparte/macos_recording.py:191-199`), et cette demande peut attendre jusqu'a 30 s (`src/aparte/macos_permissions.py:51-92`). Le plan ne parle que du `dispatcher.close()` borne a 5 s, mais apres ce timeout, `controller.shutdown()` peut bloquer sur le verrou du controleur jusqu'a la fin de la demande TCC ou de l'ouverture PortAudio. C'est un gel du fil principal potentiellement bien superieur a 5 s.

Il manque une decision ferme sur `PROCESSING`. Aujourd'hui `shutdown()` abandonne une capture live en `RECORDING`, mais ne joint pas le worker de transcription en `PROCESSING` (`src/aparte/macos_recording.py:162-173`). Comme ce worker est daemon (`src/aparte/macos_recording.py:255-259`), une terminaison peut perdre une transcription en cours et laisser un `.wav` temporaire jusqu'au balayage ulterieur. Pour M6, je choisirais : update refuse tout etat non-`idle`; Quit pendant `recording` abandonne explicitement; Quit pendant `processing` attend un delai borne ou refuse avec notification. Mais il faut trancher avant implementation.

Il manque une lecture coherente pour le minuteur. Ajouter `recording_seconds` n'est pas juste lire une chaine atomique : il faudra stocker `_recording_started_at`, le mettre a jour sous le verrou au meme moment que l'etat, le remettre a `None` a l'arret, en erreur et au shutdown, et lire `(state, started_at)` sous le meme verrou. Sinon le tray peut afficher un temps residuel ou `None` pendant une transition.

Il manque des tests pour les chemins de libelles qui cassent facilement : aucun raccourci configure, raccourci invalide dans le fichier, echec d'inscription publie dans `HotkeyState`, et affichage via `safe_hotkey_label()` plutot que `hotkey_label()` nu. Un fichier de config edite a la main ne doit jamais faire tomber le tray.

Il manque la liste complete des chaines visibles fr/en pour l'update. Le plan liste les libelles principaux du tray, mais pas tous les retours visibles de `current`, `available`, `dirty`, `manual`, `no_upstream`, `offline`, `error`, `applying`, `restarting`, ni le refus "dictée en cours". La contrainte du projet est stricte : toute chaine visible existe en francais et en anglais.

Il manque un comportement observable quand le tray macOS ne peut pas se construire. Sous Linux, le tray est une commodite; ici M6 est le correctif au principal defaut d'usage M8. Un `build_tray()` qui avale toute exception et retombe silencieusement sur une app invisible recree le bug que M6 doit fermer. Je garderais le fallback pour `ImportError`/dependance absente, mais je journaliserais ou notifierais les echecs inattendus, et j'ajouterais un check `doctor` si possible.

Il manque le traitement du bouton web de mise a jour sur Darwin. `/api/update/apply` est volontairement 404 sur macOS (`src/aparte/desktop.py:42-49`, `tests/test_desktop.py:426-438`), mais l'UI web existante affiche encore un bouton d'application quand une version est disponible. Si M6 livre le chemin tray, il doit au moins eviter de laisser un autre chemin visible et casse, ou documenter explicitement que ce reliquat reste M7.

Il manque une validation native courte dediee a M6, distincte de "les tests mocks passent". M8 a montre que les fakes Linux ne voient pas les echecs natifs (`docs/plan-portage-macos-m8.md:5-10`). La checklist M6 doit couvrir : apparition de l'icone, template clair/sombre, absence de vol de focus au lancement, timer, changement d'etat au premier appui, Quit, Ctrl-C sous rumps, update refuse pendant dictée, et fallback sans rumps.

## 4. Ce que je remettrais en question

Je remettrais en question l'absence d'action "Demarrer / Arreter la dictee", mais je ne la bloquerais pas si c'est une decision produit explicite. Le point faible est bien identifie dans le plan : sur une installation neuve, `Settings.hotkey` est vide, donc le tray observation-only peut etre le seul element natif visible mais pas le seul declencheur. C'est coherent avec la decision d'Alexandre, mais il faut assumer que M6 ne rend pas une installation neuve entierement pilotable depuis la barre de menus.

Je remettrais en question le titre vide pendant `processing`. Le micro n'est plus ouvert, donc le besoin principal est satisfait, mais l'utilisateur vient de demander une transcription. Un court indicateur textuel ou une icone distincte peut eviter un deuxieme doute : "est-ce que ca travaille encore ou est-ce termine ?" Le plan peut choisir "rien", mais ce choix doit etre teste sur la perception native.

Je remettrais en question le polling fixe a 0,25 s en permanence. Le cout CPU est probablement negligeable, mais l'etat `idle` est le cas dominant. Un timer 0,25 s seulement pendant les premieres secondes / pendant `recording`, puis 1 s au repos, serait plus propre. Ce n'est pas un blocage : 4 lectures de chaine par seconde restent acceptables.

Je remettrais en question le "deux lignes" pour `_installed_extras()`. Depuis le tray, `rumps` est forcement importable, donc detecter `rumps` suffit peut-etre a preserver `[macos]`. Mais si une future CLI update existe sur Mac sans tray fonctionnel, il vaut mieux detecter au moins `AppKit` ou un framework PyObjC utilise. Le test doit decrire la semantique : preservation des extras effectivement presents, pas installation automatique de tout `[macos]` sur Darwin.

Je remettrais en question le choix de garder `notify()` plutot que `rumps.notification()` uniquement a cause du bundle M7. C'est raisonnable pour M6, mais le plan global macOS avait note que les notifications natives attribuees au bundle etaient preferables. Je ne bloquerais pas M6 la-dessus, mais il faut garder cette dette explicitement rattachee a M7.

Je remettrais en question le niveau de silence du fallback sans tray. "Serveur comme avant" est techniquement robuste, mais produit-faible sur Mac : "comme avant" veut dire invisible. Si rumps manque, `doctor` et une notification de demarrage devraient dire clairement que l'indicateur de micro n'est pas disponible.

Verdict provisoire : l'architecture centrale est bonne, surtout sur la boucle unique et la propriete du controleur. Je ne validerais pas le plan "en l'etat" tant que la signature de run loop, les chemins de terminaison rumps, le blocage au shutdown, et le restart/update macOS ne sont pas resserres.
